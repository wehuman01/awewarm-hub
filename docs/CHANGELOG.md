# Changelog

## v0.6.1

`invite extend awi_... --expires-in 7d` pushes an invite's expiry out from now, answering both "these codes expire too soon" and "this one already expired": expiry is derived, never stored as a state, so an expired code is pending again the moment the new timestamp lands and pairs anew — no re-mint, no re-sending codes. The verb stays honest to its name: it only moves the expiry out (shortening is refused with the revoke-and-mint-a-fresh-code pointer), a used invite is refused because expiry only gates pairing and its tenant authenticates by token, and a revoked code stays revoked across the extend — the hint to `restore` rides along. The duration spells exactly like mint's `--expires-in` and is required (no silent 48h default on a code the operator believes they placed).

## v0.6.0

**Opt-in tenant key storage, off by default: `awewarm-hub config --persist-keys on|off`.** A hub restart wipes every API key from RAM, and a user whose machine is offline at that moment has their warm-ups held until it returns. For such users the operator may now allow per-connection key storage on the box: with the switch on (default off, warns when enabled), a user's own confirmed opt-in (`awewarm config set <id> --persist-key on` — their client gates every enabling command behind a prompt) stores the key in their workspace's `keys.json` (plaintext, 0600, same trust level as tenants.json), and a restart keeps their connections ticking with no re-push. Withdrawal is instant from either side: the user turns their flag off (the key is deleted), the operator flips the switch off (every stored key on the box is purged at once, adopted live by a running serve like the caps), and revoking or deleting an invite — or the v1→v2 migration removing a tenant — purges that tenant's keys while the workspace otherwise stays, as always. Persisted pushes against a hub with the switch off are refused with 403 text naming the operator knob. The setting lives in the registry's serve record and survives serve restarts; `config` displays it.

`list users` and `status --details` render LAST SEEN in the tenant's own timezone (its first connection's zone, else the box's, offset spelled out), so the column compares cleanly against the tenant's own `awewarm status` footer. The `/v1/state` view now carries `hubVersion`, which that footer prints as `awewarm-hub <version> (engine awewarm <version>)`.

## v0.5.9

Revoking an invite now frees the suspended tenant's RAM workspace: the config/state mirror and — the point — the API-key keyring leave memory the moment the suspension lands, whether the revoke ran inside the serve process or in a one-shot operator CLI (a running serve drops it on its next registry refresh). The workspace files stay on disk and `restore` reloads them lazily; keys return the way they do after a serve restart — the user's machine re-pushes them on its sync cycle, and slots that come due in between are held and catch up rather than fail.

## v0.5.8

`--help` command listings now wrap long one-liners instead of truncating them with `...` (a local `WrapGroup`, same behavior as awewarm's), so a narrow terminal still reads every description in full. It is inlined rather than imported from awewarm on purpose — a help-rendering nicety must not move the `awewarm` engine pin.

`invite revoke awi_... --delete` wipes an invite row from the ledger outright: no revoked tombstone stays, a used one takes its tenant with it (token dead, capacity slot freed, workspace kept on disk), and `restore` cannot bring any of it back. Plain revoke still keeps every row; `--delete` also accepts an already-revoked row — the purge-a-tombstone case. Taking the tenant along is not optional: authorization lives on the invite row alone, so a tenant whose invite row vanished would come back unsuspended with the global machine cap.

The capacity caps are now settings, not launch arguments: `awewarm-hub config --max-tenants 20 --max-conns-per-tenant 10 --max-machines 2` retunes them at any time and a running serve adopts the new values without a restart (caps live in the registry's serve record, which every tenant action and each scheduling tick re-read; serve flags still stamp them at launch, and unset flags resolve to the saved values). `config` alone shows what is in effect and where it comes from, `--reset` clears the caps back to the 10/5/1 defaults, and with cap flags `--data-dir` becomes a one-shot registry selector like on every other command (alone it still persists the machine's default data dir). `status` shows pre-set caps even before a first launch, and the "hub is full" error now names the config knob.

`invite` becomes a group holding the whole invite lifecycle: bare `awewarm-hub invite [flags]` still mints exactly as before (the README's one-liner is untouched), and `invite rename awi_... <name>`, `invite revoke awi_... [--delete]`, `invite restore awi_...` nest the per-code verbs beside it — symmetric with `list`, the read-side group. A group-level `--data-dir` reaches subcommands that don't carry their own. **Breaking:** the pre-0.5.8 top-level `revoke` / `restore` keep working as hidden aliases that print their new spelling (removed in v1.0); the top-level `rename` never shipped in a release and simply moved. User-facing guidance (`status`, engine errors, revoke's undo hint) now names the new spellings.

`invite rename awi_... <name>` relabels an invite's note after minting — the label `list invites` and `list users` show; a used invite's tenant carries a copy set at join time and follows, so both listings stay in agreement. Non-destructive: code, status, caps, and expiry untouched.

## v0.5.7

`list invites --token` shows the tenant token behind each used invite, so a user who lost theirs (reinstall, new machine) is handed back the same identity — connections, quotas, workspace — instead of re-pairing into a fresh tenant: they reconnect with `awewarm remote connect <url> --token <it>`. The flag is the old name back with honest semantics: `--token` originally *was* the code-reveal flag, renamed to `--reveal` in awewarm because it showed codes, not tokens.

This changes a stable design constraint, eyes open: tenant tokens now join invite codes as the deliberate on-disk plaintext, kept in `tenants.json` for exactly this recovery (authentication still compares the token's SHA-256 hash — the auth path is untouched). The exposure widens accordingly: a data-dir reader could already spend a pending invite; now they can also act as an existing tenant (push connections, read state — never read API keys, which still live in RAM only). Docs and help text now state the rule as "invite codes and tenant tokens are the on-disk exceptions; guard the data dir". Tenants that joined before this release show `—` (the token wasn't kept) and keep the fresh-invite path; `--json` follows `--token` the way it follows `--reveal`.

**Breaking:** `invite` learns batch minting and adopts aweshare's flag spellings: `--name` (was `--note`), `--count N` (1–100 codes in one registry transaction, sharing name, expiry, and machine cap), and `--expires-in 90s|30m|12h|7d` (was `--expires-hours`; same 48 h default, now also accepting sub-hour spellings). The old flags are gone — spellings match `aweshare hub invite create` across the two products.

## v0.5.6

**Breaking:** revoke/restore converge to the invite code as their single entry point, and the code becomes the only ledger of authorization. `revoke awi_...` kills a pending code or suspends the tenant that used it (token rejected, connections stop ticking, capacity slot freed) — `revoke t_...` / `restore t_...` are gone and now error with a pointer to `list invites --reveal` (the USED BY column names the tenant). The code is the lifetime name of an authorization: once used, its `usedBy → tenant` link is permanent, so tenant-addressing was always a second address for the same state transition — with a second code path, which had already drifted (the `t_` path wiped machine pairings, the `awi_` path didn't).

Authorization state now lives in exactly one place: the invite's `revokedAt`. The tenant-level `suspendedAt` mirror is deleted — suspension (auth 401s, tick skipping, capacity counting, `list users`) derives from the invite, so there is no sync logic to drift. Revocation no longer touches machine pairings at all: revoke/restore is a pure, lossless authorization act; a user who reinstalled or changed machines gets a fresh invite (new tenant, new quota), or the operator raises the `machines` value on their invite row in `tenants.json` — a running serve adopts disk edits.

Machine caps are layered: the invite carries its own `machines` value, stamped at minting by `invite --machines N` (defaulting to `serve --max-machines`); auth enforces the value on the code, falling back to the global cap for codes minted before caps moved onto them. `list invites` shows each code's cap, and the over-limit 403 now points users at the operator for a new invite instead of the removed revoke+restore reset. `status`' machines line and every operator-facing string now speak the single entry point.

The registry migrates once, in `Hub.__init__` under the cross-process lock, v1→v2: tenant-level `suspendedAt` moves onto the corresponding invite's `revokedAt`, and invite rows minted before codes were kept on disk — unaddressable by code — are dropped together with the tenant they produced (its token dies with the row; its workspace stays on disk, and the user re-pairs with a fresh invite). Upgrade the package and restart `serve` together so both processes speak registry v2. Hub users need nothing: the client passes server messages through verbatim, and the wire protocol is unchanged. Hub version numbering diverges from awewarm's from here (the engine dependency is untouched, still pinned `>=0.5.5,<0.6`); the CLI surface is now `invite [--machines N]` / `list invites` / `list users` / `revoke <awi_>` / `restore <awi_>`.

## v0.5.5

First release of awewarm-hub as its own package, split out of awewarm — open-source under the same MPL-2.0, at [wehuman01/awewarm-hub](https://github.com/wehuman01/awewarm-hub). `awewarm-hub serve` replaces `awewarm serve --hub`, and every `awewarm hub ...` command moves here under the `awewarm-hub` prefix; an existing `~/.awewarm-server` data dir (tenants, invites, the persisted `config --data-dir` setting) carries over unchanged — stop the old serve, `pip install awewarm-hub`, start again. Hub *users* keep using plain awewarm exactly as before: pairing (`remote connect <url> --invite awi_...`) and delegated-connection sync are untouched, and awewarm 0.5.5's tombstones point the old spellings here. The engine underneath (WarmServer, schedule, transport, the HTTP handler core) comes from the `awewarm` pip dependency, pinned `>=0.5.5,<0.6`, so the wire protocol stays in lockstep with the open-source client. Most of what ships here grew up in awewarm's tree after its v0.5.0 and never shipped in an awewarm release; this changelog carries it from here on.

Invites and tenants: the operator mints one-time codes (`invite --note alice`, 48 h default, `--expires-hours` to change); pairing mints a token and marks the code used. `tenants.json` stores only SHA-256 hashes of tokens, so pairings survive a restart, while API keys live in server RAM only and are re-pushed by each user's machine after one. Every tenant gets a private workspace — connections, state, and the RAM keyring are invisible across tenants. `list users` renders health, usage, and machines plus the code each tenant joined with (masked by default, `--reveal` for full text); `list invites` shows every minted code and its fate (pending / used / expired / revoked). Capacity is set at serve time: `--max-tenants` (default 10, counting active tenants only) and `--max-conns-per-tenant`; a light per-tenant rate limit (60 requests/minute) stops a looping client.

Revocation is suspension, not deletion, and works from either handle: `revoke t_...|awi_...` suspends a tenant or kills a pending invite; `restore` undoes either, re-taking a capacity slot and refusing when the hub is full. A suspended tenant frees its slot. A token serves one machine by default (`--max-machines` raises the cap); revoke + restore clears a token's paired machines.

`status` is the operator's one-glance dashboard: tenants against the max, delegated connections against the per-tenant cap, invite counts by fate, the data dir, and a best-effort liveness probe of the local serve ("NOT reachable" is information, not an error). `--details` appends every delegated connection across tenants with its mode, next due moment, and timezone. Serve stamps its caps into `tenants.json` at launch so one-shot CLI processes on the same box read the same numbers; a data dir whose serve never launched says "caps unknown" instead of guessing.

Hub registry mutations (join, revoke, restore, usage writes) hold a cross-process transaction lock shared by the resident serve and one-shot CLI processes — a stale usage/last-seen write can no longer overwrite a concurrent revoke and revive the tenant's token. The server also reloads `tenants.json` when it changes underneath a long-lived serve, so invites minted or tenants revoked by separate CLI processes take effect without a restart.

`config --data-dir` persists the default data dir on the hub machine (the flag overrides once, `--unset` clears); `self-update [--check]` upgrades from PyPI.

The documentation suite now mirrors awewarm's, and the two packages cross-reference each other in docs and metadata. README.md was rebuilt with the full awewarm-style header (hero banner, PyPI/license/status badges, Ko-fi, the Support section) and a section explaining who runs which package; README_cn.md is its Chinese mirror; README.ai.md is the agent-facing operator protocol; docs/CONTRIBUTING.md records the engineering doctrine and the hub's stable design constraints; `resources/skills/awewarm-hub/SKILL.md` is the installable operator skill (via aweskill or direct copy); a CI workflow mirrors awewarm's matrix. Version numbering now runs in lockstep with the engine — both packages ship v0.5.5, and the dependency pin is `awewarm>=0.5.5,<0.6`.
